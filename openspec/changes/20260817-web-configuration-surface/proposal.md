# Proposal: Configuration through the web interface

**Change ID:** 20260817-web-configuration-surface
**Date:** 2026-08-17
**Status:** Implemented (API surface; front-end form not built)
**Author:** flg

---

## Problem Statement

The web interface can watch and steer a collective but cannot configure one.
Its routes cover observation and action — snapshots, prompts, oversight
decisions, governance proposals, diagnostics — and none of them writes
configuration. A grep of its write routes confirms this: prompt, infuse,
oversight, test-llm, governance decisions and diagnostics runs, and nothing else.

The practical effect is a discontinuity in the most-demonstrated surface. The web
interface is what gets shown to someone who is not going to open a terminal, and
the moment configuration is needed the answer becomes "connect to the host and
edit five files".

Configuration is also the place a graphical surface genuinely beats a command
line. A schema-driven form makes the silent failure class — an unresolvable model
reference, a missing credential name — structurally impossible rather than merely
detectable.

## Current Behavior

Observation and action routes only. No configuration read or write. All
configuration is per-host files edited by hand.

## Desired Behavior

A configuration surface in the web interface, driven by the configuration
schema, that:

* presents valid choices rather than free text where the schema knows them
  (available models for a role mapping, declared catalogs, known roles);
* validates before saving, using the same checks the preflight command uses;
* shows what will change and requires confirmation;
* records who changed what.

The governance question is not optional here. Some configuration is ordinary
(display preferences, endpoints) and some is **posture** — whether the deployment
auto-executes structural changes, oversight timeouts, the signing floor. Changing
posture from a browser without approval would be a governance regression, so the
surface must distinguish the two classes and route the second through the
oversight path.

## Success Criteria

- A role's model mapping can be changed in the browser, with only valid values
  offered, and takes effect after the documented restart.
- An invalid combination cannot be saved.
- Posture changes are distinguished from ordinary configuration and gated.
- Every change is attributed and recorded.
- Read-only users cannot reach the configuration surface.

## Scope

**In scope**

- Schema-driven read and write of configuration through the web interface.
- Validation shared with the preflight checks.
- Class distinction between ordinary configuration and posture, with gating.
- Attribution and recording.

**Out of scope**

- Editing secret values in the browser.
- Free-text YAML editing (which would defeat the purpose).
- Configuring a deployment other than the one being served.

## Implementation options

**A. Generated forms from the schema.** Least bespoke code, and the surface
improves automatically as the schema grows. Generated forms are rarely pleasant
without effort.

**B. Hand-built pages for the few things operators actually change** (role→model,
catalogs, posture), with everything else remaining file-based. Better ergonomics
for the common case, and a permanent split between what the UI can and cannot do.

**C. Generated by default with hand-built overrides** where the generated form is
poor.

B is tempting and C is more honest about where this ends up. Both depend on the
schema existing first.

> This section is deliberately open. The contract above is what must hold; the
> mechanism below is a starting point, not a decision. Anyone implementing this
> is expected to improve on it.

## Open questions

1. Does configuration through the browser go through the oversight queue? For
   posture, almost certainly yes; for a model mapping, probably not — and the
   line needs drawing rather than assuming.
2. What authorisation separates "may view" from "may reconfigure"? The interface
   has authentication but not this distinction.
3. Does the surface apply changes live where possible, or always require the
   documented restart?

## Assumptions

- The configuration schema change lands first; this is a surface over it.
- Secret values remain out of scope for any interface.
